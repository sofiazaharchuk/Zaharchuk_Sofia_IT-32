Це підтверджує, що `PRAGMA foreign_keys = ON;` реально активна на з'єднанні.

## Завдання 5 — звірка з ER-діаграмою (Практика 3)
Структура повністю відповідає діаграмі: назви таблиць (`rooms`, `guests`, `bookings`), назви колонок і напрямки обох FK (`room_id → rooms.id`, `guest_id → guests.id`) збігаються з тим, що було спроєктовано. Змін не вносилось.

## Контрольні питання

**1. Навіщо PRAGMA foreign_keys = ON;, якщо FOREIGN KEY уже в CREATE TABLE, і чому це доводиться повторювати на кожному новому з'єднанні?**

Оголошення `FOREIGN KEY ... REFERENCES ...` у `CREATE TABLE` саме по собі нічого не забороняє — це лише опис зв'язку. У SQLite фактична перевірка цього зв'язку вимкнена за замовчуванням через історичну сумісність. `PRAGMA foreign_keys = ON;` — параметр конкретної сесії (з'єднання), а не файлу бази: якщо відкрити той самий `.db` в іншій програмі чи новому підключенні й не виконати цю команду знову, перевірка знову буде вимкнена, навіть якщо щойно працювала в попередньому сеансі.

**2. Яка принципова різниця між PRIMARY KEY і FOREIGN KEY?**

`PRIMARY KEY` унікально ідентифікує рядок **власної** таблиці — значення не повторюється і не може бути NULL. `FOREIGN KEY` — колонка, значення якої посилається на первинний ключ **іншої** таблиці й тим самим фізично реалізує зв'язок між таблицями. Одна колонка технічно може бути одночасно і зовнішнім ключем, і частиною первинного ключа своєї таблиці, але це різні ролі, не синоніми.

**3. Чим ON DELETE CASCADE відрізняється від ON DELETE RESTRICT, і чому різні студенти можуть обґрунтовано обрати різну дію для одного й того самого зв'язку?**

`RESTRICT` забороняє видалення батьківського рядка, доки на нього є хоч одне посилання — СУБД відмовляє в операції. `CASCADE`, навпаки, автоматично видаляє всі залежні рядки разом з батьківським. Вибір завжди залежить від бізнес-сенсу конкретного домену: якщо залежні рядки мають самостійну історичну чи фінансову цінність — доречний `RESTRICT`; якщо вони без батьківського запису повністю втрачають сенс — доречний `CASCADE`. Тому для одного й того самого типу зв'язку різне трактування бізнес-логіки може обґрунтовано вимагати різної дії.
